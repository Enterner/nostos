# nostos 内核规范（职责边界与立项标准）

> 单一事实源：本文件裁决「什么进内核、什么不进」。产品仓
> `docs/nostos-开发观察.md` 的一切内核侧立项，以本文件的准入清单为准；
> 本文件与产品仓 AGENTS.md 的内核边界摘要冲突时，以本文件为准。

## 一、内核的定位

nostos 是**进程内插件运行时内核**：提供可逆副作用的运行时与一条跨编译器稳定的
动态插件边界。它宿主在操作系统之上，不是 OS 内核；它的消费生态是具体产品（如
ithaca），不是开放的应用市场。

职责取两条主流纪律的交集：

| 参照系 | 本职（nostos 对齐的部分） | 明确排除（nostos 同样排除） |
|---|---|---|
| OS 内核（Linux / NT / Zircon / seL4） | 资源记账与回收、生命周期、IPC、冻结的调用边界、模块加载 | 应用协议（无 HTTP/SSE/URL）、文本引擎（无 regex/JSON）、配置分层合并、日志框架、进程树策略封装——内核只做机制，策略与协议永远在上面 |
| 插件框架内核（OSGi Equinox / Chromium Mojo / VS Code ext host） | 生命周期事务、服务注册与依赖契约、事件、动态加载、能力门控 | HTTP（Jetty 是 bundle 不是 framework）、日志（LogService）、配置（ConfigAdmin）——即使生态需要，也放在内核**之上**的 service 层 |

两条纪律的共同内核：**机制与策略分离**、**framework 不含 service**。nostos 的
任何存量与提案都按这两条受检。

## 二、内核实现什么（职责面，现状即全部）

| 层 | 内容 |
|---|---|
| L0 可逆副作用 | `svc_id`（编译期身份）、`guard`/`Disposable`（任意 RAII 收养）、`scope`（LIFO 逆序回滚）、`plugin_scope`（ABI 门面）、`executor`（调度接缝）、`error`（点名诊断） |
| L1 组合层 | `registry`（服务注册）、`event`（事件总线：类型化/raw/slot 三路快照派发）、`context`/`di`（取用即依赖 + 编译期契约）、`component`/`host_builder`（激活即事务、依赖者先行回滚）、`published`（跨 ABI 服务表） |
| L2 插件边界 | `abi/*`（冻结 C 契约，只追加 + struct_size 门控）、`loader`/`linked_plugin`（动态/静态同构驱动）、`plugin_session`（校验/回滚/状态机） |
| 最小插件 SDK | `kit/subscriptions.hpp`（订阅清单 RAII）——C ABI 边界的直接配套，除此之外内核不携带 SDK 便利层 |

## 三、内核不实现什么（负面清单，逐条机械可判）

1. **应用协议不进内核。** HTTP/1.1、SSE、URL 解析、HTTP 客户端等属于消费方的
   服务层。主流 OS 内核不含任何应用协议；OSGi 生态需要 HTTP 时以 bundle 交付，
   不在 framework 本体。
2. **文本/数据处理引擎不进内核。** regex 引擎、JSON 库、模板引擎等。OS 内核
   从未携带文本引擎；这类件在消费方仓按共享头纪律收编。
3. **策略不进内核。** 配置分层优先级、实现选择/热切策略、审批策略、代理规则、
   日志策略等。内核层出现写死的策略值（如代理直连规则）即违规。
4. **OS 已提供机制的封装不进内核。** 子进程生命周期、管道捕获、环境块构建等
   ——OS 调用本身即机制，封装属消费方的 SDK 便利，由消费方仓收编。
5. **第三方应用库不进内核（零依赖承诺）。** 不 vendored JSON 库等应用级依赖；
   第三方库随消费方仓分发。
6. **UI、业务逻辑、文件格式处理不进内核。** （编辑格式、预览转换、审批流等
   应用层知识永远在插件/宿主。）

## 四、立项准入清单（新增内核能力的六问，全部通过才可立项）

1. 是**机制**而非策略？（策略 ⇒ 消费方）
2. 不是协议/引擎/框架？（是 ⇒ 消费方）
3. OS 未提供、或提供的形式不足以支撑 C ABI 边界？（OS 已提供且封装无 ABI 关联
   ⇒ 消费方薄封装）
4. 不引入第三方依赖（含 vendored）？（引入 ⇒ 拒绝）
5. 有 ≥2 个无关联消费方，**或**为 C ABI 冻结面的直接配套（投递纪律、载荷寿命、
   订阅退订这类 ABI 语义的调用点表达）？（两者皆无 ⇒ 留消费方）
6. 其撤销/回滚语义可经 Scope/guard 表达？（不可表达 ⇒ 不能进 L0/L1）

判定流程：提案在产品仓 `docs/nostos-开发观察.md` 记观察（绑定触发场景）→ 按六问
逐条过 → 全过才在内核仓立项；任一不过 ⇒ 由消费方仓（产品 `shared/` 或插件私有）
收编，观察文档记录裁决依据。

## 五、消费方的对应纪律

内核不做的能力件去哪里：产品仓 `shared/`（产品级共享头，准入 ≥2 个插件消费，
宿主/壳经同一裸名取用——`vckit/` 平台件、`nlohmann/` vendored 库）；单消费者
头留在所属插件。共享头的准入与 include 纪律见产品仓 AGENTS.md「目录与 include
纪律」，与内核标准共同构成完整的分层约束。

## 六、保证什么（内核价值的七条不变式，改动不得破坏）

1. **激活即事务**：任一 activate 抛异常 ⇒ 已激活组件与失败者半成品全量回滚，start 可重试。
2. **取用即依赖**：依赖边在取服务时记录；撤销时依赖者先行回滚，不存在悬垂边。
3. **逆序即安全**：先提供后取用 ⇒ 声明序即拓扑序 ⇒ 回滚无需环检测。
4. **回滚不会失败**：dispose/deactivate 必须 noexcept，违例 std::terminate。
5. **名称哈希即身份**：跨编译器稳定；typeid 只在同一 ABI 域内做类型安检。
6. **ABI 只追加**：struct_size 逐字段门控 + abi_version ⇒ 新旧宿主/插件互容忍。
7. **诊断点名**：编译期与运行期的错误消息永远指认具体组件/服务/插件路径。
